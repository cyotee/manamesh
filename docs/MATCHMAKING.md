# ManaMesh Table Matchmaking Design

## Status
**Draft** — For engineering review before implementation

## Context

ManaMesh currently has a DHT-based discovery module (`packages/frontend/src/p2p/discovery/dht.ts`) that focuses on WebRTC connection establishment via room codes. This system handles **peer connectivity** — creating/joining sessions — but not **table discovery** — browsing and selecting games to join.

For poker (and future card games), we need a richer matchmaking layer that supports:
- **Browsing available tables** (stakes, player count, game type)
- **Joining existing tables** (with seat reservations)
- **Creating new tables** (as host)
- **Real-time seat updates** (players joining/leaving, ready states)
- **Up to 10 players per table**

This design extends the existing P2P layer with a **Gossipsub-based lobby layer** on top of the existing DHT infrastructure.

## Why Both DHT and Gossipsub?

### DHT — Stable Metadata

The DHT is well-suited for **infrequently changing** data:
- Table ID and room code (stable)
- Stakes/buy-in (set at creation, doesn't change)
- Game type and rules (static)
- Host peer ID (stable for session duration)
- Max players (set at creation)

**Limitation**: DHT records propagate to k-closest peers and use eventual consistency. Provider records have ~22hr republish intervals. Not suitable for high-frequency updates like seat-by-seat changes.

### Gossipsub — Live State

Gossipsub is designed for **frequently changing, ephemeral** data:
- Available seats (changes as players join/leave)
- Ready-up states (changes frequently pre-game)
- Player presence/heartbeats (constant during lobby)
- Lobby chat or emote signals

**Advantage**: Gossipsub's Peer Exchange (PX) lets nodes re-discover topic members without centralized registries. Flood publishing ensures new announcements reach the network quickly.

## Key Design Decisions

### 1. Game-Agnostic by Design

The matchmaking layer operates on **generic table metadata** — not game-specific fields. Game type is a string field (`"poker"`, `"war"`, `"gofish"`). Future games add themselves by registering their game type identifier.

```typescript
// GameModule interface already has `id` field — matchmaking uses it directly
interface TableMetadata {
  tableId: string;       // Unique, generated by host
  roomCode: string;      // Human-readable, 6-char
  gameType: string;      // e.g., "poker", "war"
  hostPeerId: string;     // libp2p peer ID of table host
  minBuyIn?: number;     // ChipToken amount (poker-specific)
  maxPlayers: number;    // Game-specific limit
  createdAt: number;      // Unix timestamp
  version: number;        // Incremented on metadata updates
}
```

### 2. Host Authoritative

The table **host** is the authoritative source for table metadata and lobby state. All seat assignments, ready states, and game start decisions flow through the host. Peers do not modify table state — they only submit requests (join, ready, leave) that the host approves.

This mirrors the design of existing ManaMesh game modules where `client: false` moves execute on the host.

### 3. Room Codes as Human-Managed Join Keys

Like the existing DHT module, room codes remain the primary human-readable join mechanism. The DHT stores table metadata keyed by room code, making lookup straightforward:
- Host creates table → DHT record at `/manamesh/1.0.0/tables/<roomCode>`
- Guest enters room code → DHT lookup → connects to host

Gossipsub topics use the room code for lobby broadcasts:
- Topic: `/manamesh/1.0.0/lobby/<roomCode>`

### 4. Two-Phase Join Flow

```
┌──────────────────────────────────────────────────────────────┐
│  Phase 1: Discovery (DHT)                                    │
│  - Guest looks up table metadata by room code                 │
│  - Receives: host peer ID, game type, stakes, max players    │
│  - Verifies: game type matches, seats available              │
└──────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────┐
│  Phase 2: Lobby (Gossipsub)                                 │
│  - Guest subscribes to /manamesh/1.0.0/lobby/<roomCode>     │
│  - Guest sends JoinRequest message                           │
│  - Host adds guest to pendingPlayers, broadcasts seatOffer   │
│  - Guest accepts seat, broadcasts JoinConfirm                │
│  - Host confirms, broadcasts PlayerJoined                     │
└──────────────────────────────────────────────────────────────┘
```

This separation ensures:
- DHT lookups are few (once per join attempt)
- Live state flows through Gossipsub (low latency, high frequency)
- Host can reject join requests before they enter the lobby

## DHT Schema

### Namespace

```
/manamesh/1.0.0/tables/<gameType>/<roomCode>
```

Example: `/manamesh/1.0.0/tables/poker/AB12CD`

### Table Registration Record (DHT)

```typescript
interface TableRegistration {
  // Identity
  tableId: string;          // UUID, unique per table session
  roomCode: string;         // 6-char human-readable code
  gameType: string;         // "poker", "war", etc.

  // Host
  hostPeerId: string;       // libp2p peer ID (multihash base58)
  hostName: string;         // Display name

  // Table config (game-specific)
  maxPlayers: number;        // e.g., 10 for poker
  minBuyIn?: number;        // ChipToken amount (poker)

  // Timestamps
  createdAt: number;        // Unix ms
  expiresAt: number;         // Unix ms (TTL, renewed on heartbeat)
  version: number;           // Monotonic counter for updates

  // Signature (host signs to prove authenticity)
  signature: string;         // Hex signature over serialized metadata
}
```

### DHT Operations

| Operation | Method | Cadence |
|-----------|--------|---------|
| Register table | `dht.put(key, value)` | On table creation |
| Heartbeat | `dht.put(key, updatedValue)` | Every 2 minutes (before 5-min TTL) |
| Deregister | Delete local record, stop republishing | On table close |
| Lookup by room code | `dht.get(key)` | On join attempt |

### Key Generation Functions

```typescript
// packages/frontend/src/p2p/discovery/matchmaking/keys.ts

export function getTableKey(gameType: string, roomCode: string): Uint8Array {
  const encoder = new TextEncoder();
  return encoder.encode(`/manamesh/1.0.0/tables/${gameType}/${roomCode.toUpperCase()}`);
}

export function getTableListKey(gameType: string): Uint8Array {
  const encoder = new TextEncoder();
  return encoder.encode(`/manamesh/1.0.0/tables/${gameType}/index`);
}
```

## Gossipsub Schema

### Topic Naming

```
/manamesh/1.0.0/lobby/<roomCode>
```

### Message Envelope

```typescript
interface LobbyMessage {
  _matchmaking: true;        // Discriminator
  type: LobbyMessageType;    // Message type discriminator
  sender: string;            // Peer ID of sender
  timestamp: number;         // Unix ms (for freshness)
  payload: LobbyPayload;     // Message-specific data
  signature?: string;        // Optional sender signature
}

type LobbyMessageType =
  | 'JoinRequest'
  | 'JoinResponse'
  | 'JoinConfirm'
  | 'JoinAck'
  | 'LeaveNotice'
  | 'ReadyToggle'
  | 'SeatOffer'
  | 'SeatAccept'
  | 'SeatDecline'
  | 'KickNotice'
  | 'GameStart'
  | 'GameAbort'
  | 'Heartbeat'
  | 'ChatMessage';
```

### Message Types

#### Join Flow

```typescript
// Guest → Host: Request to join table
interface JoinRequest {
  type: 'JoinRequest';
  displayName: string;
  requestedSeat?: number;       // Optional preferred seat
  metadata?: Record<string, unknown>; // Game-specific (e.g., buy-in amount)
}

// Host → Guest: Accept or reject
interface JoinResponse {
  type: 'JoinResponse';
  accepted: boolean;
  seatOffered?: number;         // Assigned seat (if accepted)
  reason?: string;              // Rejection reason (if rejected)
  currentPlayerCount: number;   // For display
}

// Guest → Host: Accept the offered seat
interface JoinConfirm {
  type: 'JoinConfirm';
  acceptedSeat: number;
}

// Host → All: Broadcast new player joined
interface PlayerJoined {
  type: 'PlayerJoined';
  playerId: string;
  playerName: string;
  seat: number;
  timestamp: number;
}
```

#### Lobby State

```typescript
// Any → All: Player left (voluntary or kicked)
interface LeaveNotice {
  type: 'LeaveNotice';
  playerId: string;
  reason: 'voluntary' | 'kicked' | 'timeout';
}

// Any (seat owner) → All: Toggle ready state
interface ReadyToggle {
  type: 'ReadyToggle';
  playerId: string;
  ready: boolean;
}

// Host → All: Game start countdown/abort
interface GameStart {
  type: 'GameStart';
  startTime: number;           // Unix ms when game begins
  seed?: string;               // Optional RNG seed for card shuffle
}

interface GameAbort {
  type: 'GameAbort';
  reason: string;
}
```

#### Heartbeat

```typescript
// Any → All: I'm still here (every 5 seconds during lobby)
interface Heartbeat {
  type: 'Heartbeat';
  playerId: string;
  seat: number;
}
```

### Peer Scoring

Gossipsub v1.1 includes **peer scoring** to mitigate spam/abuse:
- Invalid message signatures → negative score
- Excessive join requests → negative score
- Valid messages from reputable peers → positive score

Hosts and bootstrap nodes should have high scores. New peers start neutral.

## Table Lifecycle

### Host Flow

```
1. Create Table
   - Generate roomCode (6-char) + tableId (UUID)
   - Set table metadata (maxPlayers, stakes, etc.)
   - Sign metadata with host key
   - Publish to DHT
   - Subscribe to lobby topic /manamesh/1.0.0/lobby/<roomCode>

2. Lobby Phase (Gossipsub)
   - Receive JoinRequest messages
   - Send JoinResponse (accept/reject)
   - Receive JoinConfirm
   - Broadcast PlayerJoined
   - Track ReadyToggle messages
   - Monitor Heartbeat messages (detect timeouts)
   - Send GameStart when ready

3. Start Game
   - Create boardgame.io game with resolved player list
   - Broadcast GameStart
   - Stop Gossipsub lobby subscription
   - Clean up DHT record (or let it expire)

4. Table Closed
   - Stop republishing DHT record
   - Send GameAbort to remaining lobby subscribers
   - Unsubscribe from lobby topic
```

### Guest Flow

```
1. Enter Room Code
   - Lookup DHT: /manamesh/1.0.0/tables/<gameType>/<roomCode>
   - Receive TableRegistration (host peer ID, metadata)

2. Verify & Request
   - Check: game type matches, players < maxPlayers
   - Subscribe to lobby topic
   - Send JoinRequest

3. Lobby Phase
   - Receive JoinResponse (accepted/rejected)
   - If accepted: send JoinConfirm with seatOffered
   - Receive PlayerJoined broadcasts (update player list)
   - Send ReadyToggle when ready
   - Monitor Heartbeat messages

4. Game Start
   - Receive GameStart
   - Connect to host via existing P2P connection
   - Join boardgame.io game
   - Unsubscribe from lobby topic
```

## Heartbeat & Staleness

### DHT Record TTL

| Field | Value | Rationale |
|-------|-------|-----------|
| Record TTL | 5 minutes | Long enough for browser tab in background |
| Republish interval | 2 minutes | 60% of TTL, ensures continuity |
| Expiry grace | 30 seconds | Allows for clock skew |

### Gossipsub Heartbeat

| Field | Value | Rationale |
|-------|-------|-----------|
| Lobby heartbeat interval | 5 seconds | Detect player disappearance quickly |
| Timeout threshold | 15 seconds | 3 missed heartbeats = disconnected |
| Score decay | Per gossipsub v1.1 | Automatic via protocol |

## Scalability

### Limits

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Max players per table | 10 | Poker standard |
| Max tables per host | 1 | Simplicity; host is CPU-constrained |
| Max pending join requests | 20 | Rate limit to prevent DoS |
| Max lobby topic subscribers | 100 | Soft limit before degradation |

### Broadcast Optimization

For lobbies with many spectators:
- **Spectator mode**: Non-playing subscribers receive only `PlayerJoined`, `LeaveNotice`, `GameStart` — not `Heartbeat` or `ReadyToggle`
- **Player mode**: Full message set

## Security Considerations

### Message Signing

All lobby messages should be signed by the sender's libp2p identity:
- `signature = libp2p.peerId.sign(serialize(message))`
- Receivers verify signature before processing

This prevents:
- Impersonation (joining as another player)
- Message forgery (fake JoinRequest, ReadyToggle)
- Sybil attacks (multiple fake players)

### Anti-Spam

| Mechanism | Implementation |
|-----------|---------------|
| Rate limiting | Max 10 JoinRequest per IP per minute |
| Peer scoring | Gossipsub v1.1 built-in scoring |
| Invite-only | Host can disable public listing |
| Nickname rules | No special characters, 3-20 chars |

### DoS Resistance

- **Lobby floods**: Peer scoring drops malicious peers
- **DHT floods**: TTL limits stale record accumulation
- **Connection exhaustion**: Max 1 table per browser tab

### Matchmaking Server (Optional)

For better UX, a lightweight relay can supplement DHT:
- Maintains a visible tables list
- Forwards join requests for NAT'ed hosts
- Uses the same message protocol
- Does **not** hold game state — purely a discovery accelerator

This matches the hybrid approach used by production P2P apps (see Pokurr, Tabletop Club).

## Alternatives Considered

### Pure DHT

**Rejected** — DHT provider records have 22-hour republish intervals and eventual consistency semantics. Seat availability changes too frequently for DHT to be practical.

### Pure Gossipsub

**Rejected** — Without DHT, there is no stable place to store "table exists at address X". Guests would need to know the topic name before joining, requiring an out-of-band discovery mechanism.

### Centralized Lobby Server

**Rejected** — Violates ManaMesh's decentralized architecture goal. A lobby server becomes a single point of failure and requires operation/maintenance.

### Pure WebRTC Data Channels

**Rejected** — Requires host to be reachable (public IP or port-forward). Doesn't work across NAT boundaries without a signaling mechanism (which the DHT provides).

## Bootstrap & Network Startup

### How ManaMesh Nodes Discover Each Other

ManaMesh uses libp2p's bootstrap system to connect peers. When a browser opens the app, it needs to find at least one peer to begin DHT queries and Gossipsub subscriptions.

#### Current Setup (Protocol Labs Bootstrap)

ManaMesh is configured with four Protocol Labs-operated bootstrap nodes:

```typescript

  '/dnsaddr/bootstrap.libp2p.io/p2p/QmQCU2EcMqAqQPR2i9bChDtGNJchTbq5TbXJJ16u19uLTa',
  '/dnsaddr/bootstrap.libp2p.io/p2p/QmbLHAnMoJPWSCR5Zhtx6BHJX9KiKNN6tpvbUcqanj75Nb',
  '/dnsaddr/bootstrap.libp2p.io/p2p/QmcZf59bWwK5XFi76CZX8cbJ4BhTzzA3gU1ZjYZcYW3dwt',
];
```

These are:
- **Public** — globally reachable via DNS
- **Stable** — operated by Protocol Labs as part of the IPFS network
- **WebSocket/WebRTC-enabled** — browsers can connect without browser extension
- **Free** — no cost to use

#### Two-Tier Bootstrapping

| Tier | Purpose | Nodes | Control |
|------|---------|-------|---------|
| **Peer discovery** | Find peers to talk to | Protocol Labs bootstrap | Third-party |
| **DHT routing** | Find who has data | Any DHT server-mode node | Shared infrastructure |
| **NAT traversal** | Connect through NATs | Circuit Relay v2 | Protocol Labs relay + ManaMesh relays (future) |

#### Browser Limitation: DHT Client Mode Only

Browsers run libp2p in **client mode**:

```typescript
dht: kadDHT({
  clientMode: true,  // Browser can query but not serve DHT records
}),
```

This means:
- Browser **can** `dht.put()` and `dht.get()`
- Browser **cannot** serve records to other peers
- DHT lookups depend on server-mode DHT nodes existing along the query path

### ENS-Based Bootstrap Discovery

#### Problem with Hardcoded Nodes

Hardcoded bootstrap nodes create a **centralization risk**: if Protocol Labs changes their infrastructure, ManaMesh nodes cannot discover each other without an app update. Additionally, hardcoded nodes are not optimized for ManaMesh's namespace and use case.

#### Solution: ENS Text Record for Bootstrap Nodes

Using ENS (Ethereum Name Service), ManaMesh can store its bootstrap node list in a **decentralized, updatable registry**:

```
manamesh.nodes.eth
  └── Text Record: "bootstrap"
      └── Value: '["/dnsaddr/relay-us-west.manamesh.io/p2p/Qm...", ...]'
```

**Flow:**

```
┌──────────────────────────────────────────────────────────────┐
│  ManaMesh App (first launch or cache expired)                │
│                                                               │
│  1. Resolve ENS: manamesh.nodes.eth                          │
│  2. Get multiaddr list from ENS text record                  │
│  3. Use those addresses to bootstrap libp2p                  │
│  4. Cache result in localStorage (TTL: 24 hours)            │
└──────────────────────────────────────────────────────────────┘
```

**Benefits:**

| Property | ENS Solution |
|----------|-------------|
| Decentralized | ENS is on Ethereum — no single point of control |
| Updateable | Owner updates ENS record via wallet — no app update needed |
| Human-readable | `manamesh.nodes.eth` is cleaner than raw peer IDs |
| Verifiable | ENS proof-of-ownership via DNS chaining |
| Low cost | ~$5-20/year for ENS name + ~$10-50 per update (gas) |

#### Implementation

#### Resolution Order

The bootstrap resolver tries sources in this order:

1. **localStorage cache** (24hr TTL) — fastest, no network call
2. **ENS text record** — decentralized, updatable, requires Ethereum RPC call
3. **Hardcoded Protocol Labs nodes** — always works, no dependency

```
┌──────────────────────────────────────────────────────────────┐
│  1. Check localStorage cache                                  │
│     └── Valid cache → return immediately                      │
│                                                              │
│  2. Resolve ENS: manamesh.nodes.eth → "bootstrap" text       │
│     └── Valid ENS record → cache + return                     │
│                                                              │
│  3. Fall back to hardcoded Protocol Labs nodes                │
│     └── Always available                                     │
└──────────────────────────────────────────────────────────────┘
```

#### Implementation

```typescript
// packages/frontend/src/p2p/bootstrap-resolver.ts

const ENS_NAME = 'manamesh.nodes.eth';
const CACHE_KEY = 'manamesh_bootstrap_nodes';
const CACHE_TTL_MS = 24 * 60 * 60 * 1000; // 24 hours

/**
 * Hardcoded Protocol Labs bootstrap nodes — always available as final fallback.
 */
const HARDCODED_BOOTSTRAP_NODES: string[] = [
  '/dnsaddr/bootstrap.libp2p.io/p2p/QmNnooDu7bfjPFoTZYxMNLWUQJyrVwtbZg5gBMjTezGAJN',
  '/dnsaddr/bootstrap.libp2p.io/p2p/QmQCU2EcMqAqQPR2i9bChDtGNJchTbq5TbXJJ16u19uLTa',
  '/dnsaddr/bootstrap.libp2p.io/p2p/QmbLHAnMoJPWSCR5Zhtx6BHJX9KiKNN6tpvbUcqanj75Nb',
  '/dnsaddr/bootstrap.libp2p.io/p2p/QmcZf59bWwK5XFi76CZX8cbJ4BhTzzA3gU1ZjYZcYW3dwt',
];

/**
 * Resolve ManaMesh bootstrap nodes.
 *
 * Priority:
 * 1. localStorage cache (fast, no network)
 * 2. ENS text record "manamesh.nodes.eth" → "bootstrap"
 * 3. Hardcoded Protocol Labs nodes (always works)
 */
export async function resolveBootstrapNodes(): Promise<string[]> {
  // 1. Check cache
  const cached = localStorage.getItem(CACHE_KEY);
  if (cached) {
    try {
      const { nodes, timestamp } = JSON.parse(cached);
      if (Date.now() - timestamp < CACHE_TTL_MS && Array.isArray(nodes) && nodes.length > 0) {
        return nodes;
      }
    } catch {
      // Malformed cache — continue to ENS resolution
    }
  }

  // 2. Try ENS text record
  try {
    const bootstrapText = await resolveEnsBootstrap();
    if (bootstrapText && bootstrapText.length > 0) {
      // Cache and return
      localStorage.setItem(CACHE_KEY, JSON.stringify({
        nodes: bootstrapText,
        timestamp: Date.now(),
      }));
      return bootstrapText;
    }
  } catch (err) {
    console.warn('[Bootstrap] ENS resolution failed, using hardcoded nodes:', err);
  }

  // 3. Fall back to hardcoded nodes
  return HARDCODED_BOOTSTRAP_NODES;
}

/**
 * Resolve bootstrap nodes from ENS text record.
 */
async function resolveEnsBootstrap(): Promise<string[]> {
  // Uses viem's ENS resolution (no wagmi hooks needed for simple resolution)
  const publicClient = createPublicClient({
    transport: http('https://eth-mainnet.g.alchemy.com/v2/' + import.meta.env.VITE_ALCHEMY_KEY),
  });

  const resolver = await publicClient.getResolver({ name: ENS_NAME });
  if (!resolver) {
    throw new Error(`ENS name ${ENS_NAME} has no resolver`);
  }

  const bootstrapText = await publicClient.getEnsText({
    name: ENS_NAME,
    key: 'bootstrap',
  });

  if (!bootstrapText) {
    throw new Error(`ENS name ${ENS_NAME} has no "bootstrap" text record`);
  }

  return JSON.parse(bootstrapText) as string[];
}

/**
 * Force a fresh ENS resolution, bypassing cache.
 * Call this from settings UI when user wants to refresh bootstrap nodes.
 */
export async function refreshBootstrapNodes(): Promise<string[]> {
  localStorage.removeItem(CACHE_KEY);
  return resolveBootstrapNodes();
}
```

### Three-Tier Bootstrap Architecture

The bootstrap resolver follows a fixed priority at all times: **cache → ENS → hardcoded Protocol Labs nodes**. As ManaMesh grows, the *content* of the ENS record changes (adding ManaMesh relay nodes), but the resolution order stays the same.

#### Tier 1: Baseline (Always Active)

Protocol Labs bootstrap nodes are the **always-available fallback**. No matter what ENS returns or what ManaMesh infrastructure exists, if all else fails the browser connects via Protocol Labs.

```
┌─────────────────────────────────────────────────────────────┐
│  Browser                                                     │
│    │                                                        │
│    └── WebSocket ──► Protocol Labs Bootstrap Nodes (fallback) │
│                      (always works, no dependency)            │
└─────────────────────────────────────────────────────────────┘
```

#### Tier 2: ENS Text Record (ManaMesh-Operated Relays)

When ManaMesh operates its own relay infrastructure (e.g., 3 globally distributed VMs), the `manamesh.nodes.eth` ENS text record is updated to include those nodes. The resolver finds ManaMesh relays first, falling back to Protocol Labs only if needed.

```
┌─────────────────────────────────────────────────────────────┐
│  Browser                                                     │
│    │                                                        │
│    ├── WebSocket ──► ManaMesh Relay (us-west-2)            │
│    ├── WebSocket ──► ManaMesh Relay (us-east-1)            │
│    ├── WebSocket ──► ManaMesh Relay (eu-west-1)            │
│    └── WebSocket ──► Protocol Labs Bootstrap (fallback)    │
└─────────────────────────────────────────────────────────────┘

Resolver behavior:
  1. Cache hit  → ManaMesh relays (from localStorage)
  2. Cache miss → ENS → ManaMesh relays
  3. ENS fail   → Protocol Labs nodes
```

**This is the target operational state.** ManaMesh owns relay infrastructure, updates via ENS, and Protocol Labs serves as the final fallback.

#### Tier 3: Dedicated DHT Servers (Production Scale)

For production with hundreds of concurrent tables, ManaMesh operates DHT server-mode nodes (not just relays). These participate in DHT routing directly, making lookups significantly more reliable.

```
┌─────────────────────────────────────────────────────────────┐
│  Browser (client mode DHT)                                  │
│    │                                                        │
│    ├── WebSocket ──► ManaMesh DHT Server + Relay 1         │
│    ├── WebSocket ──► ManaMesh DHT Server + Relay 2         │
│    ├── WebSocket ──► ManaMesh DHT Server + Relay 3         │
│    └── WebRTC ──────► ManaMesh Circuit Relay               │
└─────────────────────────────────────────────────────────────┘
```

### Critical Mass & Reliability

#### When Does DHT-Based Discovery Work Reliably?

DHT routing quality depends on **server-mode DHT nodes** existing along lookup paths. The k-closest peers for a given key may not all be available.

| Player Count | DHT Server Density | Expected Behavior |
|-------------|-------------------|------------------|
| 1-10 | Bootstrap nodes only | Inconsistent — records may not propagate |
| 10-50 | Bootstrap + few community nodes | Partial — some lookups succeed |
| 50-200 | Growing community servers | Improving — DHT routing stabilizes |
| 200+ | Stable ecosystem | Reliable — k-bucket routing works |

**Honest assessment**: DHT-based discovery will be inconsistent until ~50+ concurrent players OR ManaMesh operates dedicated relay nodes. For early adoption, join codes remain the reliable fallback.

### Operational Considerations

#### If ENS Resolver Is Down
- Fallback to `FALLBACK_BOOTSTRAP_NODES` (hardcoded Protocol Labs nodes)
- localStorage cache (24hr TTL) provides resilience

#### If All Bootstrap Nodes Fail
- Join codes work without any bootstrap (peer connection via manual SDP exchange)
- Existing `fallbackAvailable: true` in current DHT module handles this

### Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| ENS resolver down | Fall back to Protocol Labs nodes (always available) |
| Stale cache | 24hr TTL + "Refresh bootstrap nodes" in settings |
| ENS name expires | Register for 10+ years or transfer to multisig |
| Ethereum RPC rate limits | Multiple RPC providers (Alchemy, Infura, Cloudflare) |
| ManaMesh relay overloaded | Horizontal scaling + geographic distribution |
| Wrong ENS record | Cache TTL limits blast radius; Protocol Labs fallback ensures connectivity |

---

### Alternatives Considered

| Approach | Decentralization | Complexity | Cost |
|----------|-----------------|------------|------|
| Protocol Labs bootstrap only | Partial (third-party infrastructure) | Low | Free |
| **Protocol Labs + ENS (chosen)** | **Full (hybrid)** | **Low** | **~$5-20/yr + gas** |
| ENS text record only | Full | Low | ~$5-20/yr + gas |
| ENS custom registry contract | Full + more features | Medium | ~$5-20/yr + gas + deployment |
| Unstoppable Domains | Full | Low | Similar to ENS |
| IPNS (IPFS) | Full | Low | Free (uses existing IPFS infra) |

The chosen approach (Protocol Labs primary + ENS fallback) provides:
- **Zero dependency on ENS** for basic functionality
- **Decentralized updatability** via ENS when ManaMesh has its own relay nodes
- **No single point of failure** — Protocol Labs ensures connectivity even if ENS is misconfigured
